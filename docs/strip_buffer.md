# 条带（strip / band）缓冲后端

> 状态：**已实施**（`MUI_CFG_OUTPUT_MODE = MUI_OUTPUT_STRIP`）
> 范围：`src/mui_conf.h`、`src/mui_out.c/h`、`src/mui_gfx.c`、各控件、`demo/`、`test/strip/`
> 目标：把"整帧缓冲"的 RAM 需求从 `W×H×2` 降到 `W×STRIP_H×2`，让 8~20KB RAM 的 MCU 也能用上缓冲后端

---

## 1. 为什么需要它

直绘后端零 RAM，代价是"屏只写不读"：

- 抗锯齿必须由调用方**手传底色**，压在图/渐变上就会算错；
- 控件要自己"先擦后画"：仪表盘中心内孔、滑块圆头越出轨道、标签变长变短……
  这些地方都得各自记住"上次占了哪块"再擦（本项目已经为此踩过两个 bug）。

全屏缓冲能一次性解决这些问题（缓冲里能回读真实底色），但 `240×320×2 = 150KB`、
双缓冲 300KB，8~20KB 的 MCU 装不下。

**条带缓冲**是折中：RAM 里只留一条横带，**同一份绘制代码按带重跑 N 遍**，每遍只保留该带的像素。

## 2. 数据流

```
mui_screen_frame(draw, ctx)                 ← 应用每帧调一次
   │
   for (y = 0; y < 屏高; y += 带高) {
   │     mui_out_band_begin(y, h)           ← 设平移量 band_y = y
   │     s_clip_base = (0, y, 屏宽, h)      ← "全屏"参照改成当前带
   │     mui_reset_clip()
   │     draw(ctx)                          ← 同一条绘制代码，第 k 遍
   │        ├─ mui_rect_fill(...)  → 裁剪到带 → mui_out_fill_rect
   │        │                                      → 缓冲行 = 屏幕 y - band_y
   │        ├─ 抗锯齿 → mui_out_read_pixel  → 读同一遍里刚画上的底色
   │        └─ 超出带外的写入 → 直接丢弃
   │     mui_out_band_flush()               ← 整条带一次性 mui_port_draw_bitmap 推屏
   }
```

关键点：**每带都是"从头画满"**，所以带与带之间没有任何依赖，
最终画面与全屏缓冲**逐像素等价**（见 §6）。

## 3. 关键设计决策

### 3.1 裁剪区基准 = 当前条带（`s_clip_base`）

条带模式下 `mui_reset_clip()` 恢复到**当前带**而不是整屏。这样应用里既有的

```c
mui_reset_clip();
mui_screen_clear(UI_BG);
... 画满整屏 ...
```

可以**原样复用**：语义自动从"画满全屏"变成"画满当前带"。
否则每次 `reset_clip` 都会把裁剪区放大回整屏，绘制量白费。

### 3.2 平移只发生在输出层

`mui_gfx.c` 及以上全部照旧用**屏幕坐标**；`mui_out.c` 内部把 `y` 平移 `-band_y`：

- `mui_out_draw_pixel / fill_rect / draw_bitmap`：带外行直接跳过（防御性，正常路径已被裁剪）；
- `mui_out_read_pixel`：带外返回 0（AA 回读，只有落在带内的像素才有意义）。

好处：图元、控件、容器、字体一行都不用改。

### 3.3 控件在条带模式下"全量重绘"

条带模式与"保留模式控件的增量缓存"天然冲突：缓存判断的是"屏上还是上次那份内容"，
而条带模式下屏上根本没有上一份内容。处理方式统一为：

| 位置 | 非条带模式 | 条带模式 |
|---|---|---|
| `xxx_draw()` 的缓存跳过 | 状态未变则 `return` | 编译期去掉跳过，一律全量重绘 |
| `xxx_set_*()` 的即时重绘 | 改状态后立刻局部重画 | **只改状态，不写屏**（帧外写屏会污染条带缓冲） |

涉及控件：`button`（状态缓存）、`gauge`（值缓存 + 中心数值擦除）、
`progressbar`（`set_value/set_pos/set_visible` 即时重绘）、`label`（6 个 setter 全部即时重绘）、
`popup`（`needs_panel` 面板缓存）。`slider / toggle / list / dropdown` 本就没有绘制缓存，无需改动。

因此条带模式下**绘制必须发生在回调里**，且控件 `draw()` 会真正重画（不再"省"）。

### 3.4 运行期带高：`mui_strip_set_height()`

缓冲按编译期上限 `MUI_CFG_STRIP_H` 静态分配，运行期可取更小的带高（测试就靠它穷举带边界）。
带高越大 → 重放遍数越少 → 越快，但同一块缓冲上限也越高。

### 3.5 不做带内自动清屏

带缓冲每遍清一次（`memset`）能在"回调没铺满底色"时兜底，但代价是每帧多写 `屏宽×屏高×2` 字节
的等效流量，在 MCU 上不划算。因此约定：**回调必须自己铺满底色**（正常界面本来就会先 `mui_screen_clear`）。
回调没铺到的地方会推出上一带的残留 —— 这是明显的花屏，容易被发现，且是使用错误而非库缺陷。

## 4. 用法

```c
/* 1) mui_conf.h（或工程编译选项）里选后端与带高 */
#define MUI_CFG_OUTPUT_MODE   MUI_OUTPUT_STRIP   /* 或 -DMUI_CFG_OUTPUT_MODE=3 */
#define MUI_CFG_STRIP_H       16                 /* 240 宽时缓冲 = 240*16*2 = 7.5KB */

/* 2) 界面写成一个"能整屏重画"的函数 */
static void app_draw(void *ctx)
{
    (void)ctx;
    mui_reset_clip();          /* 条带模式下"全屏" == 当前条带 */
    mui_screen_clear(UI_BG);
    /* ... 画全部内容（含控件 draw）... */
}

/* 3) 每帧：先改状态（输入/动画），再交给整帧绘制通道 */
void app_frame(void)
{
    poll_input();              /* 只改状态，不要在这里画 */
    update_animation();
    mui_screen_frame(app_draw, NULL);   /* 条带：回调被按带调用 N 次并逐带推屏 */
}
```

要点：

- 不要再用"直接画 + `mui_screen_flush()`"的写法；`mui_screen_flush()` 在条带模式下是空操作；
- 回调内可以照常使用 `mui_set_clip` / `mui_clip_save` / 容器 `begin/end`（会与带裁剪求交）；
- 回调**不要**改动画/输入状态（那部分每帧只做一次，放在回调外）。

## 5. 代价与取舍

| 后端 | 静态 RAM（240×320） | 相对速度 | 能否回读底色 |
|---|---|---|---|
| 直绘 | ~0 | 1.0× | 否（AA 要手传底色） |
| 全屏单缓冲 | 150KB | ~1.0×（多一次推屏） | 是 |
| 全屏双缓冲 | 300KB | ~1.0× | 是 |
| **条带缓冲（带高 32）** | **15KB**（10 遍） | 慢于全屏（每遍有图元启动开销） | 是 |
| **条带缓冲（带高 16）** | **7.5KB**（20 遍） | 更慢 | 是 |
| **条带缓冲（带高 8）** | **3.75KB**（40 遍） | 最慢 | 是 |

代价的本质：**像素总量不变，但"每个图元的启动成本"要乘以遍数**。
全屏填充类界面（大面积色块）几乎不亏；由大量小图元组成的界面亏得明显。
选取原则：**在 RAM 允许的前提下取尽可能大的带高**。

## 6. 怎么验证"条带不影响结果"

两条独立证据（都在 CI 可跑）：

1. **`build\mui_test_strip.exe`** —— 渲染同一场景，把带高取 `1/2/3/5/7/13/16/32`，
   要求与"带高 = 上限"的参照帧**逐像素完全一致**（带高 1 意味着每行都是带边界，最苛刻）；
   另外断言：同一帧连画两次结果一致（重放幂等）、帧外 `set_*` 不写屏但下一帧体现新状态、全程零越界违规。
2. **截图三方对照** —— `demo_shot.png`（直绘）、`demo_shot_strip.png`（条带）、
   以及用 `-DMUI_CFG_OUTPUT_MODE=1` 编出的全屏缓冲截图：

   | 对比 | 差异像素 |
   |---|---|
   | 直绘 vs 全屏缓冲 | 60 |
   | 直绘 vs 条带 | 60（同一批） |
   | **条带 vs 全屏缓冲** | **0** |

   那 60 个像素全部在抗锯齿边缘上，源于"缓冲后端能回读真实底色、直绘只能用手传 `bg`"这个
   **既有的、文档化的**后端差异，与条带无关（条带与全屏缓冲完全一致即为证明）。

## 7. 已知限制 / 后续

- **要求界面可重放**：`app\app_ui.c` 目前是逐处局部重画的增量写法，要用条带后端需先补一个
  "按当前页全量重画"的 `app_ui_draw()`（`demo\demo_ui.c` 已是两种写法并存的样板）。
- **未做"只重放脏带"**：目前每帧都把 N 条带全部重放。若应用在状态变更处调用
  `mui_dirty_mark()`，可在帧首取 `mui_dirty_bounds()` 跳过无关带 —— 这是后续最容易拿到的性能提升。
- **未做 DMA 推带**：`mui_out_band_flush()` 目前同步调用 `mui_port_draw_bitmap`，
  有 DMA 的平台可在此处改成异步 + 双带乒乓。
- **未做带内并行/重叠**：单缓冲条带，推带期间无绘制（可加第二块带缓冲做乒乓隐藏推屏时间）。
